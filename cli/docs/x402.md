# x402 clients and payment outcomes

Use an existing wallet through its own x402 SDK/client, or explicitly choose a
configured CLI signer. Inspection and external-client use do not require importing
a private key or creating a Regent wallet. See [agent wallets](agent-wallets.md).

`regents x402 details` sends the specified URL, method, headers and body without a
payment signature. An unprotected endpoint may execute that HTTP operation, so
inspection is not a guarantee that the endpoint itself is read-only.

The additive `payment_required_response` field is the complete PaymentRequired
object, including all offered schemes, networks, exact amount strings and
extensions. The older `accepts` convenience list filters to locally supported
terms. External clients use the complete object and retain their original request
credentials and body. Suggested follow-up commands use placeholders and never
reconstruct private headers or bodies. Without a challenge, `ok`, `status`,
`body_text` and `content_type` describe the actual HTTP result, including errors.
MCP keeps public protocol signatures, offer tokens and payment receipts while
excluding private transport/signing credentials. SIWA receipt redaction is unchanged.

The raw `quote`, `prepare`, `fetch` and `refund` flow uses atomic token amounts.
The USDC-budget `pay` path supports exact Base or Base Sepolia USDC for the Regent
rail, using [Circle’s published USDC contract addresses](https://developers.circle.com/stablecoins/usdc-contract-addresses). Other assets and batch deposits require the raw atomic flow: a deposit is
not the same accounting quantity as a quoted service charge. Approval fingerprints
are checked before another request is sent. The Regent HTTP client rejects
redirects for both discovery and payment, so authenticated and signed requests
cannot be silently redirected to another origin.

## Managed Agentic Wallet adapter

The adapter is pinned to AWAL 2.10.0. Its CLI supports `--method`, JSON `--data`,
`--headers`, `--max-amount` and `--correlation-id`. Regent forwards methods and
canonical JSON object/array bodies. AWAL reparses the body, so whitespace-changing
JSON, numbers that cannot round-trip exactly, primitives and arbitrary raw bodies
are rejected before dispatch. Caller headers are rejected because AWAL does not
expose redirect control. Use the Regent rail or an external client for those
requests. The provider manages its own redirects and payment policy; Regent's
local allowed-host budget is not enforcement inside that provider.

Limits must fit AWAL's safe-integer atomic amount argument. Every new paid command
is independent. Unknown flags, repeated singleton flags, missing values, explicit
boolean values and extra positional arguments are rejected before payment work.
Confidential body arguments and URLs are removed from command echoes; raw subprocess
errors, stdout and stderr are not copied into error causes.

The pinned CLI prints its companion's JSON result. `paymentMade === true` with an
exact nonnegative `amountPaid` identifies provider-reported USDC spend, not
independent chain proof. Process exit zero, a payment ID, or HTTP success alone
cannot establish settlement or actual spend. Safe product data and public payment
references remain intact. The adapter records reported spend rather than charging
the maximum reservation as though it were actual spend.

## Results and recovery

`payment_status` is separate from HTTP `ok` and `status` (or `http_status` for
`pay`). Its values are `settled`, `not_paid`, `not_required` and `unknown`. Local
settlement status describes the endpoint's settlement response, not a separate
chain verification. A payment can settle while the product request returns 500.
An HTTP 200 without payment evidence can still have unknown settlement.

Before a potentially consequential local payment phase, the runtime saves a
`receipt_id` and marks the existing intent used. Lost responses retain that receipt
and `intent_id`; the CLI never automatically repeats the same paid attempt. Read
it with `regents x402 receipts get --id <receipt-id> --json`.

Budget-aware calls expose `reservation_id`; managed calls also send that identifier
to AWAL as `provider_correlation_id`. Unknown outcomes or unknown actual spend keep
the reservation held. Inspect `regents budget ledger --budget <budget-id>`, the
provider's correlation record, local receipt and product outcome before authorizing
another operation. There is no new automatic reconciliation or external-receipt
import mechanism. Existing local budgets are accounting checks on this command
path, not signer-enforced delegation or custody.

A local share receipt records a reference supplied by the caller. Its existence
is not proof of payment, product delivery or revenue. Previously saved receipts
are not rewritten.
