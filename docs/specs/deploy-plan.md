# Executive assessment

The codebase has a **strong security and product-architecture thesis**, especially around identity separation, onchain truth, deny-by-default Ash policies, wallet-signed value movement, protected data, and contract authority. The operational guides are unusually conservative and correctly treat Autolaunch deployment as **NO-GO**.

The supplied snapshot is nevertheless **not a release candidate**. I found **nine P0 integration or launch blockers**, several of them in the first-playable capabilities:

* Every application-shell route targets a LiveView module absent from the supplied tree.
* Staking action preparation is missing required envelope fields and will raise.
* Staking and redemption confirmation validators are called without required validation context and therefore cannot pass.
* The lazy-auth refactor, current Privy bridge, application entrypoint, and tests implement incompatible contracts.
* Standard production endpoint configuration is incomplete.
* Clean-checkout setup invokes `npm ci` without a lockfile, while the documented setup/reset scripts are absent.

I would describe this as **a well-designed pre-alpha with substantial vertical implementations, but a partially integrated branch**, rather than “nearly done” relative to the full Regents end state. It could become nearly done relative to the narrower first-playable milestone after the P0 and P1 work below.

That distinction matters because your founder directives correctly say that onchain state wins for value settlement, browser state is downstream, actions are deny-by-default, and submitted transactions are not success until receipt verification and rereconciliation. 

## What is already strong

**Chain and transaction boundaries are thoughtful.** Contract addresses, ABIs, selectors, constants, and permitted action shapes are pinned in a canonical manifest. The browser re-encodes calldata, verifies signer, target, chain and zero native value, simulates before sending, and returns submitted hashes to the server. The source and served OpenAPI files are identical, and the declared `base-mainnet.json` evidence hash matches the actual file.

**The Ash model is mostly well shaped.** Separate `Human` and `System` actors, named domain actions, non-public generic mutations, and explicit policy checks fit the intended architecture. Ash requires all applicable policies to authorize, so the existing use of layered policies can provide useful defence in depth when their overlap is intentional. ([Hexdocs][1])

**The protected human-account mapping is cautious.** `HumanAccount` maps the existing protected table rather than inventing a second account graph, and migration generation is disabled for that resource.

**Notebook and discussion safety have received real attention.** Markdown output is sanitized, notebook artifacts are restricted to approved runtime/origin declarations, and the notebook iframe is cross-origin, credentialless, sandboxed, referrer-free, and denied device/payment capabilities.

**The operational guides are directionally excellent.** They separate deployment, routine multisig work and emergencies; prohibit blind signing and plaintext keys; require decoded simulation and code-hash checks; emphasize two-step ownership; and explicitly state that no Autolaunch action is presently admitted.

# Main architectural changes I would make

## 1. Establish one authoritative shell owner

Implement the accepted persistent `AshPlatformWeb.ShellLive` and let it own route dispatch, `handle_params/3`, async destination loading, presentation-query canonicalization and failure isolation. Do not maintain separate shell behavior in every destination LiveView.

The alternative is to remove `ShellLive` from the router and route directly to the existing LiveViews, but that would fight the stated persistent-shell architecture. With no current users, this is the right moment for a clean cutover rather than a compatibility layer.

## 2. Replace ephemeral wallet-action state with a durable Ash state machine

Create one canonical resource such as `WalletAction` or separate `StakingAction`/`RedemptionAction` resources with at least:

* Unique action and idempotency keys.
* Human account, expected signer, chain, target, value and calldata hash.
* Reviewed action type and argument digest.
* Preparation expiry.
* Approval and primary transaction hashes.
* States such as `prepared`, `approval_submitted`, `submitted`, `included`, `confirmed`, `reverted`, `confirmed_unreconciled` and `reconciled`.
* Receipt block number/hash and the finality level attained.
* Action-specific pre-state and reconciliation evidence.

The browser should be able to submit a given hash repeatedly, but the server should never allow a second transaction to masquerade as a retry. Browser memory and `sessionStorage` should remain recovery hints, never the state owner.

## 3. Separate signing authorization from transaction confirmation

A ten-minute prepared-action signature is appropriate for asking a wallet to sign. It is not an appropriate lifetime for confirming a transaction that may remain pending or require later operator reconciliation.

Use:

* A short-lived signed preparation envelope.
* A durable server record created at preparation or first submitted-hash registration.
* Indefinite verification of that registered hash, subject to retention policy.
* Explicit abandonment rules that never turn “retry verification” into “resend”.

## 4. Treat external provisioning and chain verification as durable workflows

Do not provision a Sprite in an Ash `before_transaction` hook and then hope the local database commit succeeds. Record intent first, call the provider outside the database transaction with a stable idempotency key, and reconcile remote success back into local state.

Ash documents that `before_transaction` hooks run before the transaction is opened, so external success can currently precede local failure. ([Hexdocs][2])

Apply the same model to chain confirmation: receipt retrieval, finality progression and post-state reconciliation should be repeatable background work, not dependent on one LiveView process remaining alive.

## 5. Make production an executable contract

Production startup should fail early with clear errors unless all of these are present and consistent:

* Approved public host and URL scheme.
* `SECRET_KEY_BASE`.
* Endpoint server enablement.
* Exact `check_origin` configuration.
* HTTPS redirection/HSTS policy.
* Attested production database target.
* Required Privy and Sprite configuration.
* Migrations already applied through a separately approved release operation.

Phoenix’s production guidance expects runtime secrets and an explicitly configured production endpoint; endpoint origin and SSL settings are security controls, not cosmetic deployment options. ([Hexdocs][3])

# Operations-guide assessment

The three guides should remain authoritative **only as guarded procedures, not transaction authority**. The deployment guide’s current NO-GO position is correct because the active manifest remains evidence-only, no Autolaunch prepared action is admitted, Solidity findings are unresolved, and branch coverage is explicitly below the stated gate. 

I would improve the guides in these specific ways:

| Improvement                                         | Reason                                                                                                                                                                                                                                          |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Add immutable front matter                          | Every runbook should name its version, source commit, active-manifest hash, approved packet hash, owner, review date and expiry/revalidation date.                                                                                              |
| Generate a read-only preflight record               | A command should read chain ID, runtime code hashes, owners, pending owners, Safe owners/threshold/nonce/modules/guard/fallback handler, balances and admitted actions, then emit signed or hashable JSON. It must never propose or broadcast.  |
| Replace generic Safe recommendations after approval | “3-of-5 preferred” is useful design guidance, but execution documents should eventually contain only the exact founder-approved Safe and threshold.                                                                                             |
| Define finality per operation                       | Deployment, ownership acceptance, routine withdrawal and emergency pause may warrant different progression from inclusion to finality. The guide should name when the next irreversible step is permitted.                                      |
| Standardize an evidence schema                      | Store proposal hash, decoded calls, simulation, reviewer, signer confirmations, receipt, internal calls, balance differences, finality and post-state in one machine-checkable format.                                                          |
| Test runbook/manifest drift in CI                   | Contract names, selectors, role names, addresses and allowed operations mentioned by a runbook should be checked against the canonical manifest.                                                                                                |
| Move the pause-only role into contract acceptance   | The emergency guide’s recommended limited pauser is a good design, but it does not exist by writing it into a guide. It requires contract implementation, adversarial tests, address/role attestation and manifest admission before deployment. |
| Add incident communications and severity            | Define severity, public-status ownership, user-facing impact language, legal/compliance escalation and criteria for closing monitoring—not just the onchain containment steps.                                                                  |

The routine and emergency guides should never gain an arbitrary “execute calldata” escape hatch. Each pause, unpause, ownership acceptance, migration, sweep or recovery operation should become a separately admitted prepared action with exact targets and argument bindings.
